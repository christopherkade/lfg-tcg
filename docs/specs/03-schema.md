# 3. Polymorphic Database Schema (PostgreSQL / Supabase)

Execute this SQL snippet in your Supabase SQL Editor. The canonical, up-to-date copy of this script lives at `supabase/schema.sql` (it also includes `DROP ... IF EXISTS` statements at the top so it can be re-run cleanly during development — remove that block before running against a project with real user data).

> **Important:** Every `preferred_*` column on `profiles` has a sensible default (see DDL below), so a brand-new profile row — created with only `id`/`username`/`discord_handle` from the Profile screen's identity form — is valid immediately without the constraints failing. This is what allows onboarding to stay a simple two-field form while the LFG search dialog (Section 5) still has real values to pre-fill with on first use.
>
> **Profile stores the _last-used_ search settings, not a fixed preference.** Game, format, playstyle, acceptable power brackets, match type, location, and desired group size are edited exclusively via the "Search" dialog on the LFG tab (not the Profile screen). Every time `createPod` runs, it both (a) updates these `preferred_*` columns to match what was just searched for, and (b) snapshots them into the new `pods` row. This keeps the dialog's next pre-fill, and the Match Feed's filtering, in sync with the user's most recent search.
>
> **`city` is the one profile column that's identity-like rather than a `preferred_*` search setting.** It's edited on the Profile screen (via `CitySelector`, alongside username/discord handle) rather than the LFG Search dialog, because it describes where the user generally is, not something they re-pick per search. `createPod`/`updatePod` still snapshot it onto each `pods` row (same pattern as the `preferred_*` columns) so the Match Feed (Section 6) can scope IRL pods by a plain column filter without joining back to `profiles`.
>
> **City is a config-driven slug, not free text — see `constants/citiesConfig.ts` (`CITIES_CONFIG`/`CITY_MAP`).** It mirrors `GAMES_CONFIG`'s extensibility pattern (Section 4): supporting a new city is a one-line addition to that array, no schema/migration needed. Using a stable slug (not the free-text `location_name` a searcher types per-pod) is what lets the Match Feed (Section 6) scope IRL pods to the viewer's city with a plain equality check instead of unreliable fuzzy text matching. `profiles.city` is optional — set once on the Profile screen (Section 5) like `username`/`discord_handle`, not part of the per-search "Search" dialog — and every `createPod`/`updatePod` call snapshots its current value onto the pod's own `city` column, the same way the other `preferred_*` columns are snapshotted onto their pod counterparts.
>
> **`pods` SELECT RLS must include accepted members, not just `status = 'ACTIVE'` or the owner.** Supabase Realtime's `postgres_changes` re-checks a table's SELECT policy against the row being changed for every single subscriber, on every event — if that check fails for a given subscriber, they simply never receive the event (no error, it's silent). If the policy were only `status = 'ACTIVE' OR user_id = auth.uid()`, then the instant a host marks their pod `MATCHED`, every accepted member's subscription would start failing that check (they're neither `ACTIVE` nor the owner), so they'd never find out: `MatchedPodWatcher`'s `MatchedDialog` wouldn't fire for them, and their own `MatchFeed` would keep showing the now-stale card forever (no event ever tells their client to refetch and drop it). The fix is allowing accepted members through the policy regardless of the pod's current `status`.
>
> **That accepted-member check must go through the `public.is_accepted_pod_member(uuid)` SECURITY DEFINER function, not an inline `exists (select 1 from pod_joins ...)`.** `pod_joins`'s own SELECT policy queries `pods` back (to check host ownership), so an inline subquery on `pods` creates a policy cycle — pods policy → pod_joins policy → pods policy → ... — which Postgres rejects with `infinite recursion detected in policy for relation "pods"`. The SECURITY DEFINER function runs as its (RLS-bypassing) owner, so its internal query against `pod_joins` doesn't re-trigger `pod_joins`'s RLS policy, breaking the cycle.

```sql
-- Baseline system enums
CREATE TYPE match_type AS ENUM ('IRL', 'ONLINE');
CREATE TYPE join_status AS ENUM ('PENDING', 'ACCEPTED', 'REJECTED');

-- 1. Profiles Table (stores user identity, plus the last-used LFG search
-- settings edited via the LFG tab's "Search" dialog)
CREATE TABLE profiles (
    id UUID REFERENCES auth.users ON DELETE CASCADE PRIMARY KEY,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    username TEXT UNIQUE NOT NULL,
    discord_handle TEXT NOT NULL,
    avatar_url TEXT,
    city TEXT,                                            -- key into CITIES_CONFIG (constants/citiesConfig.ts), optional (NULL if unset, e.g. Online-only players)
    preferred_game TEXT NOT NULL DEFAULT 'MTG',          -- e.g., 'MTG', 'POKEMON', 'ONE_PIECE', 'LORCANA'
    preferred_format TEXT NOT NULL DEFAULT 'COMMANDER',  -- e.g., 'COMMANDER', 'STANDARD' (one of GAMES_CONFIG[game].formats)
    preferred_playstyle TEXT NOT NULL DEFAULT 'casual',  -- 'casual' or 'competitive'
    preferred_brackets INT[] DEFAULT ARRAY[1,2,3,4,5],   -- multi-select 1-5, only for preferred_game == 'MTG'
    preferred_match_type match_type NOT NULL DEFAULT 'ONLINE',
    preferred_location_name TEXT,                        -- required (non-empty) if preferred_match_type == 'IRL', else NULL
    preferred_max_players INT NOT NULL DEFAULT 2 CHECK (preferred_max_players BETWEEN 2 AND 6),
    last_pod_created_at TIMESTAMP WITH TIME ZONE,        -- stamped by enforce_pod_creation_cooldown (supabase/sql/rate_limits.sql); drives the 15s pod-creation cooldown
    last_join_request_at TIMESTAMP WITH TIME ZONE,       -- stamped by enforce_join_request_cooldown (supabase/sql/rate_limits.sql); drives the 10s join-request cooldown
    CONSTRAINT bracket_conditional_check CHECK (
        (preferred_game = 'MTG' AND preferred_brackets IS NOT NULL AND array_length(preferred_brackets, 1) > 0 AND preferred_brackets <@ ARRAY[1,2,3,4,5]) OR
        (preferred_game != 'MTG' AND (preferred_brackets IS NULL OR array_length(preferred_brackets, 1) IS NULL))
    ),
    CONSTRAINT location_conditional_check CHECK (
        (preferred_match_type = 'IRL' AND preferred_location_name IS NOT NULL AND length(trim(preferred_location_name)) > 0) OR
        (preferred_match_type = 'ONLINE' AND preferred_location_name IS NULL)
    )
);

-- 2. Pods Table (active LFG requests, snapshotting the host's profile settings)
CREATE TABLE pods (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    user_id UUID REFERENCES profiles(id) ON DELETE CASCADE NOT NULL,
    game_key TEXT NOT NULL,
    format_key TEXT NOT NULL,        -- e.g., 'COMMANDER', 'STANDARD'
    playstyle_key TEXT NOT NULL,     -- 'casual' or 'competitive'
    power_tiers INT[] CHECK (power_tiers IS NULL OR power_tiers <@ ARRAY[1,2,3,4,5]), -- snapshot of profiles.preferred_brackets if MTG, NULL otherwise
    type match_type NOT NULL,        -- 'IRL' or 'ONLINE'
    location_name TEXT,              -- E.g., 'Local Game Store Name' (Null if ONLINE)
    city TEXT,                       -- snapshot of profiles.city at creation/edit time; drives Match Feed IRL scoping (Section 6)
    scheduled_at TIMESTAMP WITH TIME ZONE, -- app-level required date/time for IRL matches (see validateStartSearchInput, not a DB CHECK); NULL for ONLINE, which falls back to created_at for display and the Match Feed's Date filter (Section 6). The submitted date+time is converted to this real instant via zonedTimeToUtc (src/lib/timezone.ts) against the timezone the host's browser reported at submit time — see the Organiser Tables subsection below for the parallel recurring_tables fix.
    max_players INT NOT NULL DEFAULT 2 CHECK (max_players BETWEEN 2 AND 6), -- Total group size including the host; snapshot of preferred_max_players. This CHECK is later re-scoped by recurring_tables.sql to allow organiser-hosted pods a much higher ceiling — see the Organiser Tables subsection below.
    reserved_slots INT NOT NULL DEFAULT 0 CHECK (reserved_slots >= 0 AND reserved_slots <= max_players - 2), -- seats the host has already filled with people outside the app (no real pod_joins row); added via supabase/sql/add_pods_reserved_slots.sql, not in the DROP-and-recreate baseline block above (see its header comment)
    notes TEXT CHECK (notes IS NULL OR length(notes) <= 300), -- Optional free-text note set in the Search dialog, one-off (not persisted onto profiles)
    status TEXT DEFAULT 'ACTIVE',    -- 'ACTIVE', 'MATCHED', 'EXPIRED'
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    expires_at TIMESTAMP WITH TIME ZONE DEFAULT (NOW() + INTERVAL '4 hours'),
    matched_at TIMESTAMP WITH TIME ZONE, -- set by markPodMatched when status -> MATCHED; drives the retention sweep below
    locked_at TIMESTAMP WITH TIME ZONE, -- set/cleared by toggleLockPod (src/app/actions/pods.ts); closes requestJoin to new joiners without changing status, reversible — see the Organiser Tables subsection below
    recurring_table_id UUID REFERENCES recurring_tables(id) ON DELETE SET NULL, -- set on pods spawned by an organiser's recurring table (see the Organiser Tables subsection below); NULL for ad hoc peer-hosted pods
    auto_accept BOOLEAN NOT NULL DEFAULT FALSE, -- denormalized from recurring_tables.auto_accept at spawn time; requestJoin checks this column directly rather than joining back to recurring_tables
    store_name TEXT -- denormalized display name for organiser-hosted pods (Match Feed's "Store Event" badge); NULL for ad hoc peer-hosted pods
);

-- Enforce a single ACTIVE ad hoc pod per user. Scoped to recurring_table_id
-- IS NULL so an organiser's own personal LFG search never collides with
-- their store's recurring-table pods, which are managed entirely separately
-- (see the Organiser Tables subsection below).
CREATE UNIQUE INDEX pods_one_active_per_user ON pods(user_id) WHERE status = 'ACTIVE' AND recurring_table_id IS NULL;

-- Guarantees spawn_due_recurring_pods() can never double-spawn a pod for the
-- same recurring table's same occurrence, even under concurrent cron runs —
-- and, since this has no `status` filter, also guarantees a manually
-- cancelled occurrence (cancelPod sets status = 'EXPIRED') never gets
-- silently re-spawned by the next hourly run either.
CREATE UNIQUE INDEX pods_one_per_recurring_occurrence ON pods(recurring_table_id, scheduled_at) WHERE recurring_table_id IS NOT NULL;

-- 3. Pod Joins (Join requests, subject to host approval)
CREATE TABLE pod_joins (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    pod_id UUID REFERENCES pods(id) ON DELETE CASCADE NOT NULL,
    user_id UUID REFERENCES profiles(id) ON DELETE CASCADE NOT NULL,
    status join_status NOT NULL DEFAULT 'PENDING',
    joined_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    matched_notified_at TIMESTAMP WITH TIME ZONE, -- set once this joiner has been shown MatchedDialog for this pod (supabase/sql/matched_notification_seen.sql); NULL means not yet shown
    CONSTRAINT unique_user_pod UNIQUE (pod_id, user_id)
);

-- 4. Notifications (persisted notification center backing the header bell)
CREATE TYPE notification_type AS ENUM (
    'JOIN_REQUEST', 'JOIN_ACCEPTED', 'JOIN_REJECTED', 'MEMBER_LEFT', 'REMOVED_FROM_POD', 'POD_UPDATED', 'POD_UPDATED_PENDING', 'POD_DESTROYED', 'POD_EXPIRED_INACTIVITY'
);
CREATE TABLE notifications (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    recipient_id UUID REFERENCES profiles(id) ON DELETE CASCADE NOT NULL,
    actor_id UUID REFERENCES profiles(id) ON DELETE SET NULL,
    type notification_type NOT NULL,
    pod_id UUID REFERENCES pods(id) ON DELETE CASCADE,
    read_at TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 5. Pod History ("Past Pods" tab, supabase/sql/pod_history.sql) — a durable
-- log that survives the Matched/Expired Pod Cleanup sweep below, since that
-- sweep hard-deletes the pods row (and its pod_joins) 24h after matched_at.
CREATE TABLE pod_history (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    pod_id UUID NOT NULL,             -- not FK'd: the source pods row is deleted by the sweep; kept for reference only
    host_id UUID REFERENCES profiles(id) ON DELETE CASCADE NOT NULL,
    game_key TEXT NOT NULL,
    format_key TEXT NOT NULL,
    playstyle_key TEXT NOT NULL,
    power_tiers INT[],
    type match_type NOT NULL,
    location_name TEXT,
    city TEXT,
    scheduled_at TIMESTAMP WITH TIME ZONE,
    pod_created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    matched_at TIMESTAMP WITH TIME ZONE NOT NULL,
    members JSONB NOT NULL DEFAULT '[]'::jsonb, -- snapshot of every ACCEPTED pod_joins member at match time: [{ id, username, discord_handle, avatar_url }, ...]
    hidden_by UUID[] NOT NULL DEFAULT '{}', -- ids of viewers who deleted this entry from their own "Past Pods" list (Screen 4); the row itself is otherwise shared/untouched
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    recurring_table_id UUID REFERENCES recurring_tables(id) ON DELETE SET NULL, -- set for organiser table-history entries (see below); NULL for ad hoc "Past Pods" entries
    store_name TEXT -- denormalized store name for organiser table-history entries; NULL for ad hoc entries
);

-- 6. Organizers (professional/store role, supabase/sql/recurring_tables.sql)
-- — a 1:1 table keyed on profiles.id rather than a profiles.role column, so
-- the frequently-queried profiles table stays untouched and "is this user
-- an organiser" is a single indexed existence check.
CREATE TABLE organizers (
    id UUID REFERENCES profiles(id) ON DELETE CASCADE PRIMARY KEY,
    store_name TEXT NOT NULL CHECK (length(store_name) BETWEEN 1 AND 80),
    city TEXT NOT NULL,               -- key into CITIES_CONFIG, same convention as profiles.city
    description TEXT CHECK (description IS NULL OR length(description) <= 500),
    verification_url TEXT NOT NULL CHECK (length(verification_url) BETWEEN 1 AND 500), -- Google Maps link, store website, or similar proof of a real, physical store — see the Organiser Tables subsection below
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 7. Recurring Tables (an organiser's standing weekly event, e.g. "Friday
-- Night Magic") — spawn_due_recurring_pods() turns a row here into a real,
-- joinable pods row on schedule; see the Organiser Tables
-- subsection below.
CREATE TABLE recurring_tables (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    organizer_id UUID REFERENCES organizers(id) ON DELETE CASCADE NOT NULL,
    store_name TEXT NOT NULL,         -- always the organiser's own organizers.store_name, re-synced on every create/edit — never client-supplied (see the Organiser Tables subsection below)
    game_key TEXT NOT NULL,
    format_key TEXT NOT NULL,
    playstyle_key TEXT NOT NULL DEFAULT 'casual',
    power_tiers INT[] CHECK (power_tiers IS NULL OR power_tiers <@ ARRAY[1,2,3,4,5]), -- optional here (unlike pods' snapshot-of-a-search version): a store's standing public event doesn't need a specific power level, NULL means "all power levels welcome"
    type match_type NOT NULL DEFAULT 'IRL', -- app-level validator restricts to IRL only for this MVP; column kept for a possible future ONLINE league
    location_name TEXT NOT NULL,      -- always the organiser's own store_name (a store only ever hosts events at itself) — not a separate form field
    city TEXT NOT NULL,               -- always the organiser's own organizers.city — not a separate form field
    day_of_week SMALLINT NOT NULL CHECK (day_of_week BETWEEN 0 AND 6), -- 0=Sunday..6=Saturday, matches JS Date#getDay()
    start_time TIME NOT NULL,         -- naive wall-clock, interpreted in this row's own `timezone` column (see next_recurring_occurrence below) — added via supabase/sql/fix_recurring_table_timezone.sql, not in the DROP-and-recreate baseline block above
    end_time TIME NOT NULL,           -- used to compute each spawned pod's real expires_at instead of a flat guess; <= start_time means the event spans midnight; also interpreted in `timezone`
    timezone TEXT NOT NULL DEFAULT 'Europe/Paris', -- IANA identifier (e.g. "Europe/Paris"), captured silently from the organiser's browser at create/edit time (Intl.DateTimeFormat().resolvedOptions().timeZone) rather than a form field; existing rows backfilled to this default — see the Organiser Tables subsection below for the caveat on organisers outside metropolitan France
    max_players INT NOT NULL DEFAULT 4 CHECK (max_players BETWEEN 2 AND 200), -- joiners needed, deliberately excluding the organiser (host) themselves — unlike an ad hoc pod, this is not "total including host"; a store's table can run much larger than an ad hoc pod's 2-6 cap. The organiser-facing "Players Needed" form field maps 1:1 onto this column (see the Organiser Tables subsection below)
    notes TEXT CHECK (notes IS NULL OR length(notes) <= 300),
    auto_accept BOOLEAN NOT NULL DEFAULT FALSE, -- when true, requestJoin inserts pod_joins as ACCEPTED directly instead of PENDING for this table's spawned pods
    lead_time_hours INT NOT NULL DEFAULT 72 CHECK (lead_time_hours BETWEEN 1 AND 336), -- how far ahead of start_time the spawned pod becomes visible
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

> **Notifications have no `message` column.** Display copy is composed client-side (`NotificationCenterProvider`'s `describeNotification()`) from `type` plus the embedded `actor`/`pod` rows — this keeps copy easy to change/localize later without needing to backfill historical rows. For notification types where the actor is the pod host (`JOIN_ACCEPTED`, `JOIN_REJECTED`, `REMOVED_FROM_POD`, `POD_UPDATED`, `POD_UPDATED_PENDING`, `POD_DESTROYED`), the embedded `pod.store_name` is shown in place of the host's `actor.username` whenever `pod.recurring_table_id` is set — i.e. an organiser's store name, not their personal account username, mirroring the same `pod.recurring_table_id ? pod.store_name : pod.profiles.username` convention `MatchFeedList`/`PodDetailDialog` already use for the pod card's byline. Types where the actor is a joining player instead of the host (`JOIN_REQUEST`, `MEMBER_LEFT`) always show `actor.username`, regardless of whether the pod itself is organiser-hosted.
>
> **Rows are inserted exclusively by SECURITY DEFINER database triggers or the `pg_cron` cleanup jobs below, never by application code.** `notify_on_pod_join_insert/update/delete` (on `pod_joins`), `notify_on_pod_update` (on `pods`), `notify_pending_joiners_on_pod_update` (on `pods`, `supabase/sql/notify_pending_joiners_on_pod_update.sql`), and `notify_on_pod_destroyed` (on `pods`, `supabase/sql/notify_pod_destroyed.sql`) — all defined alongside the RLS policies in `supabase/schema.sql` (except the two split out into their own tracked `supabase/sql/` scripts) — cover, respectively: a new join request (host notified), a request accepted/rejected (joiner notified), an accepted member leaving (host notified), the host editing an already-live pod's details (every accepted member notified via `POD_UPDATED`, and separately every still-`PENDING` requester notified via `POD_UPDATED_PENDING` — a distinct type since the requester hasn't joined yet and the accepted-member copy would misstate that), and a pod being cancelled or replaced before it ever matched (every accepted member notified). The `sweep-inactive-active-pods` `pg_cron` job (`supabase/sql/inactive_pod_cleanup.sql`, see the Inactive Pod Cleanup subsection below) inserts the remaining `POD_EXPIRED_INACTIVITY` type directly, with `pod_id` left `NULL` since the pod is deleted in the same statement. Driving this from triggers/cron rather than the server actions in `src/app/actions/` means every current and future mutation path gets consistent notification coverage automatically, and lets `notifications` ship with **no client-facing INSERT policy at all** — a user can never fabricate a notification for someone else. A `MATCHED` status transition is deliberately **not** one of these types; it already has its own dedicated blocking `MatchedDialog` UX (via `MatchedPodWatcher`, see Section 5's Join Request Flow step 6), not a notification-center entry.

> **`auto_delete_rejected_pod_join()` (SECURITY DEFINER, `supabase/sql/fix_pod_joins_auto_delete_rejected.sql`) deletes a `pod_joins` row the instant it's rejected**, via an `after update ... when (old.status = 'PENDING' and new.status = 'REJECTED')` trigger on `pod_joins` — the requester no longer has to click "Dismiss" (`leavePod`) themselves before the unique `(pod_id, user_id)` constraint frees up for a fresh `requestJoin`. It runs alongside `notify_on_pod_join_update` above (both are AFTER UPDATE triggers on the same event, so the `JOIN_REJECTED` notification insert is unaffected), and its own nested `DELETE` can't trigger a spurious `MEMBER_LEFT` since `notify_on_pod_join_delete` only fires `when (old.status = 'ACCEPTED')` — by the time this trigger's delete runs, the row is already `REJECTED`.
>
> **`pod_history` rows are likewise inserted exclusively by a SECURITY DEFINER trigger, never by application code.** `snapshot_pod_history` (`supabase/sql/pod_history.sql`) fires on every `pods` UPDATE and inserts a snapshot row only on the `ACTIVE -> MATCHED` transition — synchronously, so the row is captured well before the Matched/Expired Pod Cleanup sweep below can ever hard-delete the source `pods`/`pod_joins` rows. `EXPIRED`/cancelled pods are deliberately **not** logged here — a "Past Pod" is defined as one that actually reached a match, not an abandoned or cancelled search. `pod_history` ships with no client-facing INSERT/UPDATE/DELETE policy, same convention as `notifications`; the one mutation a viewer can trigger — deleting an entry from their own list — goes through a separate SECURITY DEFINER RPC, `hide_pod_history_entry`, described next to the SELECT policy below.

> **Abuse/spam guardrails are enforced at the database level, not just in the server actions** (`supabase/sql/rate_limits.sql`), so a direct API call can't bypass them either. `enforce_pod_creation_cooldown()` (a `BEFORE INSERT` trigger on `pods`) rejects a new pod with `RATE_LIMITED_POD_CREATE` if `profiles.last_pod_created_at` for that user is under 15 seconds old, then stamps it; `enforce_join_request_cooldown()` (a `BEFORE INSERT` trigger on `pod_joins`) does the same against `profiles.last_join_request_at` with a 10 second cooldown. Both are deliberately a simple last-action-timestamp check rather than a sliding-window counter table — no new infra, and it's enough to stop rapid-fire spam without needing to count requests over a rolling window. `createPod` (`src/app/actions/pods.ts`) and `requestJoin` (`src/app/actions/joins.ts`) catch these raised messages and surface a translated, friendly error instead of the raw Postgres exception.
>
> **Account deletion goes through a SECURITY DEFINER RPC, `delete_own_account()` (`supabase/sql/account_deletion.sql`), not a plain client-side delete.** Deleting from `auth.users` isn't something the anon/authenticated role can do directly, and this project has no service-role Supabase client set up anywhere, so — mirroring `hide_pod_history_entry`'s existing RPC convention — the function itself does the privileged work: it first anonymizes this user's entries inside *other* users' `pod_history.members` snapshots (username → "Deleted User", handle/avatar cleared) for any row they didn't host, since that JSONB snapshot isn't FK'd to `profiles` and wouldn't otherwise be touched by cascade deletes; then it deletes the `auth.users` row, which cascades through the existing FK chain above (`profiles` → `pods`, `pod_joins`, `notifications` as recipient, `pod_history` as host) exactly as it would for any other `ON DELETE CASCADE`. `deleteAccount()` (`src/app/actions/profile.ts`) calls this RPC, signs the (now-deleted) session out, and redirects to `/login`.

> **`get_games_played_count()` (`supabase/sql/pod_history.sql`, patched by `supabase/sql/public_profile_stats.sql`) is a read-only SECURITY DEFINER RPC, not a plain `select` against `pod_history`.** It backs the History screen's lifetime "Games Played" stat (Section 5's Screen 4) and deliberately counts every row where the target user is `host_id` or in `members` — including ones that user has since hidden from their own Past Pods list via `hide_pod_history_entry`. A plain client-side `select` would go through the SELECT policy above, which excludes hidden rows, silently shrinking an achievement-style counter just because someone decluttered their history view — bypassing RLS via `security definer` is what keeps those two concerns (what you see vs. what you've actually done) independent. Takes an optional `p_user_id uuid default auth.uid()` (added by the patch below) so it can also report *another* user's count, not just the caller's own — every existing zero-arg call site is unaffected by the default.
>
> **`get_profile_pod_stats()` (`supabase/sql/profile_pod_stats.sql`, patched by `supabase/sql/profile_pod_stats_people_met.sql`, further patched by `supabase/sql/public_profile_stats.sql`) is a second read-only SECURITY DEFINER RPC, mirroring `get_games_played_count()`'s exact host-or-member/`hidden_by`-ignoring criteria.** It backs the Profile screen's "People Met"/"IRL Games"/"Online Games" stat cards (Section 5's Screen 1) and returns all three counts (`people_met`, `irl_count`, `online_count`) as a single row. `people_met` counts distinct people the target user has shared a matched pod with — de-duplicated by `profiles.id`, not `discord_handle`, since a handle can change between matches (self-corrects on every login, per the Authentication section) while the id never does. It's computed by collecting, over every `pod_history` row the target user appears in as host or member, the *other* party's id (the row's `host_id` when they were a member, each `members` entry's id when they were host) into a `union`ed set and counting it distinct, always excluding the target user's own id. One RPC call instead of three keeps the Profile page's `Promise.all` from paying for extra round trips.
>
> **Both functions take an optional `p_user_id uuid default auth.uid()`, added by `supabase/sql/public_profile_stats.sql` (Section 5's Public Profile Side Panel).** This is what lets the public profile side panel show *another* user's stats, not just the caller's own. The patch drops each zero-arg function before recreating it with the new parameter — adding a parameter is a new signature, and `create or replace` can't retarget an existing zero-arg function to a new arg list; it would silently create a second overload instead, leaving the old zero-arg one live alongside it. The `default auth.uid()` is what keeps every existing zero-arg caller (`/profile/page.tsx`, `/history/page.tsx`, `HistoryEntriesList`'s refetch) working unchanged. Both stay `authenticated`-only (no `anon` grant) — showing another user's lifetime counts is no bigger a privacy surface than `profiles` SELECT already being open to any authenticated user (below).
>
> **`mark_matched_notification_seen(p_pod_join_id)` (`supabase/sql/matched_notification_seen.sql`) lets a joiner stamp `pod_joins.matched_notified_at` on their own row, mirroring `hide_pod_history_entry`'s RPC convention** — the `pod_joins` UPDATE policy below is host-only (for Accept/Reject), so a joiner has no other way to persist "I've seen the MatchedDialog for this pod." Before this existed, `MatchedPodWatcher` tracked "already shown" purely in `localStorage`, keyed per-browser; on a new device that set started empty, and its on-mount check has no time bound (it just asks "am I an ACCEPTED member of a pod that is currently MATCHED"), so any pod matched at any point in the past — even before that device ever logged in — looked brand new and re-triggered the dialog. `matched_notified_at` makes "already shown" a durable, per-row, per-device-independent fact instead.

> **`get_platform_activity_stats()` and `get_recent_platform_activity(p_limit)` (`supabase/sql/platform_activity_stats.sql`) back the "platform activity" trust signal** (`PlatformActivityTicker`, Section 5), rendered as an always-on banner at the top of the Pods screen — a cold-start mitigation surfacing real first-party activity (never seeded/fake data) so an empty or sparse feed doesn't read as "this app is dead." `get_platform_activity_stats()` returns `active_pod_count` (`pods` where `status = 'ACTIVE' AND expires_at > now()`), `matched_last_24h`, and `matched_last_7d` (both from `pod_history.matched_at`, deliberately ignoring `hidden_by` — the same aggregate/lifetime-counter convention as `get_games_played_count()` above). `get_recent_platform_activity` returns a small, recency-ordered list unioning recent `pods.created_at` rows (`event_type = 'CREATED'`) and recent `pod_history.matched_at` rows (`event_type = 'MATCHED'`), each row carrying only `game_key`/`format_key`/`type`/`event_at` — structurally no PII (no `user_id`/`host_id`/`username`/`city`/`location_name`/`notes`/`members`), enforced by the function's own `SELECT` list rather than by RLS, so a future column added to `pods`/`pod_history` can't leak through it silently. Neither function's aggregate favors a live `pods`-sourced "created in the last 24h" count, since `inactive_pod_cleanup.sql`/`matched_pod_cleanup.sql` sweep that table on windows that don't align with `created_at` — a count sourced from it would silently under-report anything swept in between; `pod_history`-backed counts don't have that problem since that table is never swept.
>
> **Both functions are also granted to `anon` in addition to `authenticated` — the only such grant anywhere in this schema.** Every other RPC and RLS policy in this project (`get_profile_pod_stats`, `get_games_played_count`, `hide_pod_history_entry`, the RLS table below, etc.) is `authenticated`-only. This grant predates the ticker becoming Pods-only (it originally also served a pre-auth signal on the Login screen); the Login screen no longer calls these RPCs, so nothing in the app currently exercises the `anon` grant, but it's left in place rather than narrowed as part of an unrelated UI change. It's considered safe specifically because each function's own `SELECT` list is the entire attack surface — SECURITY DEFINER bypasses RLS, but only a handful of non-identifying columns/aggregates are ever returned — a materially smaller surface than opening an anon SELECT policy on `pods`/`pod_history` directly (which would expose `host_id`, `city`, `location_name`, `scheduled_at`, `notes`, and the `members` roster). No rate-limiting guards this read (`supabase/sql/rate_limits.sql`'s cooldowns cover mutations only); `get_recent_platform_activity`'s `p_limit` is clamped server-side (`GREATEST(1, LEAST(p_limit, 20))`) as its only abuse guard.

### Realtime

Enable Supabase Realtime replication on the `pods`, `pod_joins`, and `notifications` tables to push instant matching feed, join-request, and notification-center updates. `pod_history` is intentionally **not** added to Realtime replication — it's a static, immutable historical log (see Screen 4 below), not a live feed.

> **`MatchFeed`, `OwnPodPanel`, and `LfgButton` share one Realtime channel instead of each opening their own.** `PodRealtimeProvider` (`src/components/PodRealtimeProvider.tsx`), mounted once around `{children}` in `src/app/(app)/layout.tsx`, opens a single unfiltered `postgres_changes` subscription on `pods` and `pod_joins` and exposes `usePodRealtime()` — `{ subscribePods, subscribePodJoins, notifyPodsChanged }` — backed by ref-held callback sets (not React state, so registering never re-renders the provider). Each of the three components registers its own existing refetch function as a callback instead of opening a channel of its own; this cuts per-tab Realtime channel count for these three from three down to one, with identical trigger conditions and identical per-component refetch behavior, since every pod mutation anywhere fans out to every open tab's channel(s) regardless of channel count. `NotificationBell` and `MatchedPodWatcher` still open their own channels (different tables/event shapes) and are unaffected — except that `MatchedPodWatcher` also calls the shared provider's `notifyPodsChanged()` (which just re-runs every registered callback, the same as a real `pods` event would) the moment it confirms a MATCHED transition through either its own realtime handler or its poll fallback. This closes a gap where a joiner's `MatchFeed` could keep showing a just-matched pod indefinitely: `PodRealtimeProvider`'s *own* `postgres_changes` delivery for that same UPDATE is a second, independent subscription and can silently fail to arrive (see the delivery-reliability note below) even when `MatchedPodWatcher`'s did — and unlike `NotificationBell`, `MatchFeed` has no poll fallback of its own to eventually self-heal, only a focus/visibility listener, which never fires for a viewer who was already sitting on a focused `/pods` tab watching for the `MatchedDialog` to appear. Unlike `MatchFeed`/`LfgButton` (whose focus/visibility-only fallback is enough since their content just sits there stale until next glanced at), `OwnPodPanel` also polls every 10 seconds while the tab is visible — a host waiting on a join request is typically staring at an already-focused `/pods` tab the whole time, so a focus/visibility listener alone would never fire (same rationale as `MatchedPodWatcher`'s poll fallback below). As with every other `postgres_changes` subscription in this codebase, `PodRealtimeProvider`'s subscription deliberately has **no `filter` param** — an earlier attempt at narrowing a subscription with `filter` was observed to silently break realtime delivery in this project (the row would exist and be visible on refetch, but the event itself never arrived at the open tab), so scoping is achieved only by reducing the number of duplicate subscriptions, never by filtering what a subscription listens to.

> **Supporting indexes (`supabase/sql/scale_indexes.sql`)** back the query patterns these realtime-triggered refetches (and `MatchedPodWatcher`'s 10-second poll fallback, see Section 7) already run constantly: `idx_pods_status_game_format_playstyle` on `pods(status, game_key, format_key, playstyle_key)` and `idx_pods_status_type_city` on `pods(status, type, city)` support the Match Feed's filtered query (the `playstyle_key` trailing column of the first index is no longer exercised by that query now that the feed doesn't filter on it, but the leading `status, game_key, format_key` columns still are), and `idx_pod_joins_user_status` on `pod_joins(user_id, status)` supports the user_id-only lookups `MatchedPodWatcher` and `LfgButton` run (the existing `unique_user_pod (pod_id, user_id)` index doesn't serve those efficiently since `pod_id` is its leading column). Purely additive — no behavior change, just keeps these already-frequent queries cheap as the active-pod set grows.

### Matched/Expired Pod Cleanup

An hourly `pg_cron` job (`sweep-matched-expired-pods`, defined in `supabase/sql/matched_pod_cleanup.sql`, applied directly in the Supabase SQL editor since this project has no tracked migrations) permanently deletes:

- `MATCHED` pods once `matched_at` is more than 24 hours old.
- `EXPIRED` pods once `expires_at` is more than 24 hours old.

The 24-hour grace window on `MATCHED` pods exists because `pod_joins` rows cascade-delete with their pod (`ON DELETE CASCADE`, above), and `MatchedPodWatcher` (Section 7) needs both rows to still exist in order to detect an accepted member's match and surface the `MatchedDialog` — an immediate delete on `markPodMatched` risks a member who wasn't actively polling missing that dialog entirely. Deleting a pod also cascades to its `notifications` rows, so any notification history tied to that pod (join requests, accept/reject, member-left) disappears with it once the sweep runs — this is accepted as intentional since `notifications` is a live inbox, not a permanent audit log. `MATCHED` pods are the one thing this sweep destroys that *does* have a durable record elsewhere: `snapshot_pod_history` (above) has already copied everything needed to render a "Past Pod" entry into `pod_history` at the moment of the `ACTIVE -> MATCHED` transition, hours before this sweep ever runs, so the Past Pods screen (Section 5) is unaffected by the deletion.

### Inactive Pod Cleanup

A separate hourly `pg_cron` job (`sweep-inactive-active-pods`, defined in `supabase/sql/inactive_pod_cleanup.sql`) closes the gap the sweep above doesn't cover: a pod that never draws a join request (or a match) stays `status = 'ACTIVE'` forever — nothing else in the app ever flips it to `EXPIRED`. This job permanently deletes any `ACTIVE` pod whose `created_at` is more than 12 hours old, first inserting a `POD_EXPIRED_INACTIVITY` notification (`pod_id` left `NULL`, for the cascade-ordering reason noted above) for the host and every `ACCEPTED` member, in one `WITH ... DELETE` statement so the insert and delete run in the same transaction.

> Unlike `sweep-matched-expired-pods`, this job also has to *tell* someone before deleting, since an `ACTIVE` pod disappearing with zero notice would look like a bug rather than expected cleanup — `matched_pod_cleanup.sql`'s sweep only ever removes pods that already transitioned away from `ACTIVE` (and, for `EXPIRED`, were already cancelled/replaced by an action that itself notified members via `notify_on_pod_destroyed`).

This 12-hour hard delete is a backstop, not the host's first signal that their search has gone nowhere — the Match Feed (Section 6) already stops returning a pod once its own `expires_at` (default `created_at + 4 hours`) lapses, so a pod with zero `pod_joins` by then is invisible to every other searcher for up to 8 hours before the sweep above ever touches it, with the host none the wiser. `NoUsersFoundDialog` (Section 5's My Pod Panel) closes that visibility gap client-side: `MyPodPanel` derives `pod.status === 'ACTIVE' && pod.pod_joins.length === 0 && now() >= pod.expires_at` on every refresh of the host's own pod (realtime/poll/focus, Section 3 above) and, when true, shows a dialog offering **Unlist Pod** (the existing `cancelPod`, flips `status` to `EXPIRED`) or **Keep Searching** (the new `extendPodSearch` server action, `src/app/actions/pods.ts`, which pushes `expires_at` to `now() + 4 hours`, the same duration `createPod` defaults to). No new column or migration was needed since this reuses `expires_at` as the trigger threshold. Choosing **Keep Searching** makes the derived condition false again on the next refetch, which closes the dialog itself — there's no separate "seen"/dismissed state to track, and no backdrop-dismiss, since (unlike the purely informational `MatchedDialog`) this dialog requires one of its two explicit choices.

### Organiser Tables (Recurring Weekly Events)

Local game stores get a separate, professional-only surface (Section 5's Organiser Dashboard screen) for publishing a standing weekly event — e.g. "Friday Night Magic" — that spawns a real, joinable `pods` row on schedule instead of a peer re-creating an ad hoc pod by hand every week. This is deliberately layered on top of the existing pod/join system rather than a parallel one: a spawned pod is a normal `pods` row (host = the organiser's own `profiles.id`), so it flows through the same Match Feed, `PodDetailDialog`, RLS, and realtime infrastructure as any peer-hosted pod, just tagged via `recurring_table_id`/`store_name`/`auto_accept`.

- **Onboarding is a hidden, self-serve funnel, not an admin-approval flow.** `/organizer/apply` (`src/app/(app)/organizer/apply/page.tsx`) is never linked from `TabBar` or anywhere else in the app — the developer shares this URL directly with trusted stores. Submitting the form (store name, city — with its own `organizer.apply.cityHelperText` copy rather than `CitySelector`'s default player-facing "near you" helper text, since a store's city isn't about scoping the viewer's own feed — a required verification link, and an optional description) calls `applyAsOrganizer` (`src/app/actions/organizer.ts`), which inserts directly into `organizers` under the `organizers_insert_self` policy (`id = auth.uid()`, above). There is no invite code or automated vetting step in this MVP; the route being unlisted is the entire gate. **`organizers.verification_url`** (a Google Maps link, store website, or similar) is required specifically because everything else about onboarding is unauthenticated trust — it's the one piece of evidence a human (the developer) can spot-check after the fact to confirm a submission is a real, physical store rather than an arbitrary self-serve signup; it is not itself validated against any external service, only checked for a plausible `http(s)://` shape client- and server-side. `requireOrganizerProfile()` (`src/lib/session.ts`) is the guard every other organiser page/action uses — it wraps `requireProfile()` and additionally requires an active `organizers` row, redirecting to `/pods` otherwise; `/organizer/apply` is the one deliberate exception, using `requireProfile()` alone since its purpose is onboarding someone who isn't an organiser yet (it redirects an already-registered organiser straight to `/organizer` instead of re-showing the form).
- **A recurring table always happens at its organiser's own store — `location_name`/`city`/`store_name` are never form fields.** `createRecurringTable`/`updateRecurringTable` (`src/app/actions/organizer.ts`) write `organizer.store_name`/`organizer.city` (from `requireOrganizerProfile()`) directly onto these three columns on every create *and* every edit, rather than accepting them from the client — a store only ever has one location, so asking an organiser to re-enter it per table would just be a chance to typo/drift from their real profile. This is the one place a "denormalized at write time" column is kept eventually-consistent with its source rather than frozen at creation: unlike a `pods` row (an immutable historical fact once spawned), a `recurring_tables` row is a live config the organiser keeps editing, so re-syncing it from the organiser's current profile on every save is the more correct behavior.
- **`next_recurring_occurrence(day_of_week, start_time, timezone)` and `spawn_due_recurring_pods()`** (both SECURITY DEFINER, `supabase/sql/recurring_tables.sql`, timezone-aware since `supabase/sql/fix_recurring_table_timezone.sql`) compute each recurring table's next occurrence and insert a `pods` row once that occurrence falls within `lead_time_hours`. `start_time`/`end_time` are naive wall-clock values with no offset of their own; both functions convert them to real instants via Postgres's `<timestamp> at time zone <table's own timezone column>` idiom, DST-aware since it reads the zone's actual UTC offset at that specific date from Postgres's zoneinfo database rather than a fixed offset — this replaced an earlier version that explicitly treated the wall-clock time as UTC, which shifted every spawned pod's displayed time by the organiser's real UTC offset for any organiser outside UTC (e.g. an organiser-picked 11:00 Europe/Paris in summer, UTC+2, rendered back to viewers as 13:00). The ad hoc IRL scheduling path (`validateStartSearchInput`, above) was fixed the same way, via a new shared helper `zonedTimeToUtc` (`src/lib/timezone.ts`) rather than Postgres `at time zone` (no server-side SQL involved in that path) — both paths now agree on real timezone math instead of both being naively UTC. The insert sets `expires_at` to the occurrence's real end datetime — computed from `recurring_tables.end_time` the same way `next_recurring_occurrence` computes the start from `start_time` (rolling to the next calendar day when `end_time <= start_time`, i.e. an overnight event) — rather than a flat `scheduled_at + 4 hours` guess or the `pods.expires_at` column default (`created_at + 4 hours`): a pod spawned days ahead of its event via `lead_time_hours` would otherwise fall out of the Match Feed's `expires_at > now()` filter (or disappear mid-event) at a time with no relationship to when the event actually runs. `pods_one_per_recurring_occurrence` (above) is the hard idempotency guarantee — scoped to `recurring_table_id IS NOT NULL` with no `status` filter, i.e. one `pods` row per `(recurring_table_id, scheduled_at)` pair *ever*, not just while `ACTIVE` — the insert's `ON CONFLICT DO NOTHING` is just a backstop. The `status`-less scoping is deliberate, not an oversight: an earlier version scoped the index to `WHERE status = 'ACTIVE'`, which meant an organiser manually cancelling their spawned session ahead of its start time (`cancelPod`, which only sets `status = 'EXPIRED'`, below) got silently undone by this exact job on its next hourly run — the occurrence was still within `lead_time_hours` and, once `EXPIRED`, no longer matched the old index's predicate, so the insert succeeded again with a brand-new pod (new id, zero `pod_joins`), reappearing as if the cancellation never happened. Dropping the `status` filter (`supabase/sql/fix_recurring_table_cancel_respawn.sql`) makes a cancel permanent for that specific occurrence with no change to this function or to `cancelPod` itself, while leaving every future week untouched, since each has its own distinct `scheduled_at`. That same script has to delete any pre-existing duplicate `(recurring_table_id, scheduled_at)` rows before the new index can even be created — the bug already produced real duplicates in prod/staging data by the time the fix was written (`CREATE UNIQUE INDEX` fails with a `23505` otherwise), keeping the `ACTIVE` row per occurrence when one exists, else the most recently created one, and cascade-deleting the rest's `pod_joins`/`notifications` (`pod_history` is unaffected, already snapshotted independently at the `ACTIVE -> EXPIRED` transition).
- **`recurring_tables.timezone`** is captured silently, not a form field: both `OrganizerRecurringTableFormDialog` (organiser side) and `LfgDialog` (ad hoc side) read `Intl.DateTimeFormat().resolvedOptions().timeZone` from the submitter's own browser at submit time and send it along with the rest of the input; `validateRecurringTableInput`/`validateStartSearchInput` fall back to `'Europe/Paris'`/naive parsing respectively if that string isn't a recognized IANA identifier, rather than surfacing a new user-facing error for an invisible field. This is correct as long as an organiser saves their table from a device physically at (or set to) their store's location — an organiser in a French overseas territory (Guadeloupe, Martinique, French Guiana, Réunion, Mayotte, New Caledonia, French Polynesia — see `CITIES_CONFIG`) whose table predates this fix needs to open and re-save it once to pick up their real zone; new tables always capture it correctly on first save.
- **An organiser's own personal LFG search stays entirely separate from their recurring-table pods.** `pods_one_active_per_user` (above) is scoped to `recurring_table_id IS NULL`, and every "does this user already have an active pod" check in the app — `createPod`'s self-expiry of the caller's existing pod, `requestJoin`'s own-active-pod guard, `fetchOwnPodData` (`src/lib/pods/ownPod.ts`), and `LfgButton`'s own inline query — adds the same `recurring_table_id IS NULL` scope. Without it, an organiser running even one recurring table would have two simultaneously-`ACTIVE` pods (their personal search plus the spawned one), and every one of those `.maybeSingle()` queries would start erroring. The conceptual line this draws is also the intended one: an organiser's personal "My Pod" surfaces (the LFG tab, `OwnPodPanel`) never show recurring-table pods at all — those are managed exclusively through the Organiser Dashboard (Section 5) instead.
- **`enforce_pod_creation_cooldown()` (`supabase/sql/rate_limits.sql`) is patched to exempt cron-spawned rows** (`new.recurring_table_id IS NOT NULL`) — otherwise two recurring tables coming due in the same hourly run would have the second insert rejected by the 15-second per-`user_id` cooldown, since both share the organiser's `user_id`.
- **Auto-accept.** Each recurring table has an organiser-configurable `auto_accept` flag, denormalized onto its spawned `pods.auto_accept` at insert time. `requestJoin` (`src/app/actions/joins.ts`) inserts the new `pod_joins` row as `ACCEPTED` directly when the target pod's `auto_accept` is true, instead of the usual `PENDING`. Because this skips the `PENDING -> ACCEPTED` transition `notify_on_pod_join_update` listens for, `notify_on_pod_join_insert` (`schema.sql`) is patched to check `new.status` and fire `JOIN_ACCEPTED` directly for this case, so the joiner is still notified. **Toggling the switch (or editing "Players Needed", below) also has to push the new value onto the currently-spawned pod, not just the template.** `setRecurringTableAutoAccept`/`updateRecurringTable` (`src/app/actions/organizer.ts`) both call a shared `syncTemplateFieldsToActivePod` helper (`update pods set ... where recurring_table_id = ... and status = 'ACTIVE'`, taking a partial `{ auto_accept?, max_players? }`) right after saving the template row — without it, since a pod is typically spawned well ahead of its event (`lead_time_hours`), the organiser's change would only take effect on the *next* spawn while the currently-live, already-visible pod silently kept whatever value it had at spawn time (a real bug caught in testing: unticking "Instant Join" had no effect on a table's already-spawned session).
- **"Players Needed" means joiners needed — the organiser is never counted toward capacity, unlike an ad hoc pod's host.** For an ad hoc pod (`store_name IS NULL`), `max_players` is the *total* group size including the host, and every capacity check adds `+1` for them (the host is never inserted as its own `pod_joins` row). Organiser recurring-table pods (`store_name IS NOT NULL`) are the deliberate exception: `recurring_tables.max_players`/`pods.max_players` store *only* the joiner count the organiser-facing "Players Needed" field on `OrganizerRecurringTableFormDialog` (Section 5) collects — no `+1`/`-1` transform at the write/read boundary. `isGroupFull` (`src/lib/pods/joinRules.ts`), called from `requestJoin`/`respondToJoin` (`src/app/actions/joins.ts`), takes a `countsHost` boolean derived from `!pod.store_name` so it only adds the host's slot for ad hoc pods; the `{count}/{max}` displays in `PodDetailDialog`/`MatchFeedList`/`OrganizerRecurringTableCard` branch on the same `pod.store_name` signal. The form's on-screen bounds stay 2-200 (`validateRecurringTableInput`), matching the column's own CHECK.
- **Locking a session closes new joins without cancelling it — deliberately manual, not tied to the occurrence's start time.** Reaching a recurring table's scheduled `start_time` has no automatic effect on its spawned pod at all — it simply stays `ACTIVE` and joinable straight through to `expires_at` like any other pod, and the organiser has no built-in signal that "the event has begun." `toggleLockPod` (`src/app/actions/pods.ts`) lets the organiser set/clear `pods.locked_at` on their own still-`ACTIVE` pod (same `user_id`/`status = 'ACTIVE'` ownership scoping as `cancelPod`), and `isPodJoinable` (`src/lib/pods/joinRules.ts`, called from `requestJoin`) rejects any new join request on a locked pod with `errors.podLocked`. Unlike `cancelPod`, this is fully reversible — clearing `locked_at` reopens the pod to new requests immediately, with existing `PENDING`/`ACCEPTED` `pod_joins` rows completely unaffected either way. It's app-layer enforced only, the same convention `status` itself already follows (the `pod_joins` INSERT RLS policy above doesn't check either column) — no RLS change was needed. The organiser's session panel (`OrganizerRecurringTableCard`, Section 5) surfaces this as a "Lock table"/"Unlock table" button next to "Cancel session," plus a "Locked" badge there and on the pod's Match Feed card and `PodDetailDialog` join button (which disables and relabels itself while locked) for anyone else viewing it.
- **Cancelling a session skips only that occurrence — the table itself keeps recurring.** `cancelPod` (`src/app/actions/pods.ts`, same call the ad hoc "Unlist Pod" flow uses) sets the spawned pod's `status` to `EXPIRED`; nothing else changes on the `recurring_tables` row. `pods_one_per_recurring_occurrence` (Section 3) is what makes this a real, permanent cancel of that week rather than a temporary pause — see its callout there for the bug this fixed. Since the organiser could otherwise read a vanished "Upcoming session" block as "did this stop the whole table?", `OrganizerRecurringTableCard` shows a same-session info message afterward (`organizer.table.cancelledInfo`, component state `justCancelled`) reusing the table's own `dayOfWeekLabel`/`startTimeLabel` (same helpers as the card header) to say the table will spawn again automatically next `{day}` at `{time}` — deliberately not a new date computation, to avoid duplicating `next_recurring_occurrence`'s timezone-sensitive SQL logic in JS a second time. The message clears itself once `fetchUpcomingPod` finds a real pod again (i.e. next week's occurrence has spawned), not on a timer or dismiss button.
- **Deleting a recurring table also expires its currently-spawned session, not just the template.** `deleteRecurringTable` (`src/app/actions/organizer.ts`) runs `update pods set status = 'EXPIRED' where recurring_table_id = ... and status = 'ACTIVE'` *before* deleting the `recurring_tables` row — it has to run first, since the delete's `ON DELETE SET NULL` (above) nulls that pod's `recurring_table_id`, after which it can no longer be targeted by this update. Without this, a still-`ACTIVE` pod whose table got deleted mid-session stayed visible and joinable in the Match Feed indefinitely (until its own `expires_at` happened to pass), with no organiser UI left to cancel it since `OrganizerRecurringTableCard` is keyed to the now-deleted `recurring_table_id` (a real bug hit in production). This also means an accepted member now correctly gets a `POD_DESTROYED` notification (`notify_on_pod_destroyed`, above) on delete, same as `cancelPod` — previously they didn't, since that trigger only fires on the `ACTIVE -> EXPIRED` transition, which deleting the template never used to cause.
- **Cron jobs** (both hourly, `supabase/sql/recurring_tables.sql`): `spawn-recurring-table-pods` calls `spawn_due_recurring_pods()`; `expire-past-recurring-pods` flips a recurring pod's `status` to `EXPIRED` once its `expires_at` (the occurrence's real end time, above) has passed (organisers don't manually "Mark as Matched" a whole table the way an ad hoc host does). That plain `UPDATE` is also what drives table history, next. The now-`EXPIRED` row then falls into the existing `sweep-matched-expired-pods` job's `EXPIRED, expires_at > 24h old` branch for eventual deletion — no separate delete logic was needed. `sweep-inactive-active-pods` (Inactive Pod Cleanup, above) is re-patched to add `recurring_table_id IS NULL` to its own `WHERE` clause — recurring pods are legitimately created up to `lead_time_hours` (days) ahead of their event and would otherwise be wrongly caught by that job's 12-hours-since-`created_at` rule.
- **A store's recurring table can hold far more players than an ad hoc pod.** `recurring_tables.max_players` allows up to 200 (vs. an ad hoc pod's 2-6), and since `spawn_due_recurring_pods()` inserts into the same shared `pods` table, `pods.max_players`'s own CHECK (`schema.sql`, originally a flat 2-6) is re-scoped by `recurring_tables.sql` to `(store_name IS NULL AND max_players BETWEEN 2 AND 6) OR (store_name IS NOT NULL AND max_players BETWEEN 2 AND 200)` — ad hoc pods stay DB-capped at 6, organiser-hosted ones get real headroom. Deliberately keyed on `store_name`, not `recurring_table_id`: the latter is `ON DELETE SET NULL`, so deleting a recurring table with an already-spawned large pod would fire that `SET NULL` as an `UPDATE` on the pod itself, which would then fail this exact CHECK if it were scoped by `recurring_table_id IS NULL` instead (a real bug hit in testing — deleting a table blew up with a `pods_max_players_check` violation). `store_name` is set once at spawn and never changes, so it stays a stable signal even after the source recurring table is gone.
- **Table history reuses `pod_history` rather than a second mechanism.** Recurring pods never reach `MATCHED` (that's an ad hoc-pod concept), so the existing `snapshot_pod_history` trigger (`ACTIVE -> MATCHED`) never fires for them — left as-is, an organiser's "Table History" screen (Section 5) would always be empty. A second, parallel trigger, `snapshot_recurring_pod_history()` (`supabase/sql/recurring_tables.sql`), fires on `ACTIVE -> EXPIRED` scoped to `recurring_table_id IS NOT NULL` only, inserting into the same `pod_history` table (now with `recurring_table_id`/`store_name` columns, above) — `matched_at` on these rows is repurposed to hold the occurrence's `scheduled_at` rather than a real match timestamp. Keeping this a genuinely separate trigger/function (not a change to `snapshot_pod_history` itself) means recurring-table history logging can never interfere with the ad hoc "Past Pods" feature or `MatchedPodWatcher`'s dialog, which only ever reacts to a `MATCHED` transition — an organiser's table lapsing hours after the event never triggers a "You've been matched!" popup for the joiner. The existing `pod_history` SELECT policy (host-or-member, above) already covers an organiser's own read access with zero policy changes, since `host_id` on these rows is the organiser's own `profiles.id`.
